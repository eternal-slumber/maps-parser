# Review Parser

Небольшое тестовое приложение для импорта организаций и отзывов из публичных страниц Яндекс Карт. Пользователь вставляет ссылку, а приложение в фоне получает данные организации, сохраняет отзывы и показывает ход работы. Уже добавленные организации можно обновлять, переключать и удалять, а отзывы — фильтровать по оценке.

> **Важно:** это учебный проект, выполненный в рамках тестового задания. Он не связан с Яндексом и не предназначен для коммерческого использования. Данные используются только для демонстрации, поэтому могут быть неполными или неактуальными. Перед другим использованием следует самостоятельно проверить [условия Яндекс Карт](https://yandex.ru/legal/maps_termsofuse/ru).

## Используемый подход и почему

Парсер загружает обычные серверные страницы отзывов:

```text
https://yandex.ru/maps/org/{businessId}/reviews/?page=N
```

В HTML такой страницы находится `script.state-view` со встроенным JSON-состоянием. Из него берутся и данные организации, и отзывы. Парсер не ищет текст по CSS-классам и не пытается собирать страницу как пользователь в браузере: нужные значения уже лежат в структурированном виде.

Этот вариант оказался самым подходящим для тестового задания:

- не нужен браузер, поэтому импорт расходует меньше памяти и проще запускается в очереди;
- страницы можно последовательно обходить через `?page=N`;
- JSON проще строго проверять и тестировать, чем меняющуюся визуальную разметку;
- для запроса не нужны аккаунт Яндекса, CSRF-токен или внутренняя подпись.

Внутренний `fetchReviews` намеренно не используется как основной путь: он привязан к сессии, CSRF и служебной подписи запроса. Headless-браузер тоже не добавлялся — для подтверждённого SSR-пути это лишняя тяжёлая зависимость. Его стоит рассматривать только как отдельный fallback, если отзывы действительно перестанут приходить в серверном HTML.

## Как проходит импорт

После отправки ссылки HTTP-запрос не ждёт завершения парсинга. Он проверяет адрес, находит `businessId`, создаёт организацию со статусом `pending` и отправляет `SyncYandexOrganization` в Redis-очередь. Сокращённые ссылки раскрываются одним запросом, при этом переход на произвольный внешний домен запрещён.

Дальше queue worker делает основную работу:

1. Загружает страницы `/reviews/?page=N` по очереди.
2. Декодирует `state-view` и ищет объект именно с ожидаемым `businessId`.
3. Из этого же объекта получает название, рейтинг, число оценок и массив отзывов.
4. Проверяет обязательные поля `reviewId`, `rating`, `updatedTime` и приводит данные к единому формату.
5. Собирает уникальные отзывы до конца доступной выдачи, но не больше 600 записей.
6. После корректного завершения одной транзакцией обновляет организацию и отзывы в MySQL.

Пока worker работает, интерфейс раз в две секунды получает статус и показывает текущий этап, число обработанных страниц и отзывов. Переключение страниц и фильтрация больше не обращаются к Яндексу: они работают с уже сохранёнными данными через API приложения. В выдаче отображается по 50 отзывов.

## Что происходит при изменении страницы Яндекса

Структура `state-view` не является публичным API, поэтому парсер не считает любой найденный JSON подходящим. Данные организации и отзывы должны находиться внутри состояния нужного `businessId`; неоднозначность считается ошибкой, а не поводом выбрать самый большой массив на странице.

Импорт завершится со статусом `failed`, если:

- `state-view` исчез, повреждён или содержит неожиданный формат;
- нужная организация не найдена либо найдена больше одного раза;
- обязательные поля отсутствуют или имеют неверный тип;
- `updatedTime` не соответствует UTC ISO-формату;
- до ожидаемого конца пришла пустая или полностью повторившаяся страница;
- Яндекс вернул CAPTCHA либо пустой ответ;
- внутренний лимит страниц закончился раньше результата.

Неполный набор при такой ошибке в базу не записывается, поэтому успешные данные предыдущего запуска не портятся. Ошибки схемы не повторяются, а временные сетевые сбои queue job пробует обработать повторно. В журнал попадают `business_id`, номер страницы и причина сбоя.

Публичная выдача Яндекса может остановиться на 600 отзывах, даже если общий счётчик больше. Это считается ограничением источника: организация получает статус `limited`, а доступные отзывы сохраняются. Равенство собранного количества общему счётчику намеренно не требуется.

## Антибан и работа с сетью

Сейчас страницы одной организации запрашиваются строго последовательно. У HTTP-клиента заданы connect timeout 5 секунд и общий timeout 20 секунд; queue job имеет таймаут 300 секунд и до четырёх попыток с паузами 10, 30 и 60 секунд. CAPTCHA распознаётся отдельно и не маскируется под пустую выдачу.

Для тестового запуска этого достаточно. Если превращать проект в регулярный массовый сбор, понадобятся общий Redis rate limiter для всех worker, случайная пауза между страницами, экспоненциальный бэкофф на `429`, `403`, timeout и CAPTCHA, а также временная остановка импорта после серии блокировок. Прокси и ротация User-Agent имеют смысл только при реальной необходимости: случайное переключение адресов внутри одного импорта скорее ухудшит ситуацию.

## Повторный импорт и история изменений

Повторное добавление той же организации не создаёт копию: запись ищется по `(user_id, business_id)`, а отзывы обновляются по `(organization_id, external_id)`. Уникальные индексы дополнительно защищают от дублей на уровне базы.

Каждый найденный отзыв получает новое `last_seen_at` и остаётся активным. Если после корректно завершённого импорта отзыв больше не приходит из источника, он сохраняется в базе с `is_active = false` и исчезает из API. При подозрительном обрыве старые отзывы не деактивируются.

Полная история снимков пока не хранится. Если она понадобится, следующий практичный шаг — добавить таблицу запусков синхронизации и связанные снимки организации и отзывов. Тогда можно будет показать не только текущее состояние, но и разницу между запусками: изменение рейтинга, текста, оценки или количества отзывов.

## Технологии

- PHP 8.4 и Laravel 13;
- Vue 3, TypeScript и Inertia 3;
- MySQL 8.4;
- Redis для очередей и кэша;
- Laravel Sail / Docker Compose;
- Pest и PHPStan.

## Локальный запуск

Понадобятся Docker Desktop и Git. После клонирования сначала установите Composer-зависимости:

```bash
docker run --rm \
    -u "$(id -u):$(id -g)" \
    -v "$(pwd):/var/www/html" \
    -w /var/www/html \
    laravelsail/php84-composer:latest \
    composer install --ignore-platform-reqs
```

Затем подготовьте окружение и запустите контейнеры:

```bash
cp .env.example .env
./vendor/bin/sail up -d --build
./vendor/bin/sail artisan key:generate
./vendor/bin/sail artisan migrate --seed
./vendor/bin/sail npm install
./vendor/bin/sail npm run build
```

Приложение откроется по адресу <http://localhost:8000>.

Данные локального тестового пользователя:

```text
Логин:  review.parser.operator+local@demo.test
Пароль: Rvp!2026_Local#Access9
```

Во время разработки фронтенд удобнее запускать так:

```bash
./vendor/bin/sail npm run dev
```

Остановить окружение:

```bash
./vendor/bin/sail down
```

## Переменные окружения

Готовые локальные значения находятся в `.env.example`.

| Переменная         | Для чего нужна           | Значение в Sail         |
| ------------------ | ------------------------ | ----------------------- |
| `APP_URL`          | адрес приложения         | `http://localhost:8000` |
| `APP_PORT`         | опубликованный HTTP-порт | `8000`                  |
| `DB_HOST`          | MySQL-контейнер          | `mysql`                 |
| `DB_DATABASE`      | база приложения          | `laravel`               |
| `DB_USERNAME`      | пользователь MySQL       | `sail`                  |
| `DB_PASSWORD`      | пароль MySQL             | `password`              |
| `QUEUE_CONNECTION` | драйвер очереди          | `redis`                 |
| `CACHE_STORE`      | драйвер кэша             | `redis`                 |
| `SESSION_DRIVER`   | хранилище сессий         | `database`              |
| `REDIS_HOST`       | Redis-контейнер          | `redis`                 |

Секреты или токены Яндекс Карт парсеру не нужны: он работает с публичными HTML-страницами.

## Что осталось за рамками тестового задания

- общий rate limiter, jitter и circuit breaker для массового импорта;
- хранение отдельных запусков и полных снимков изменений;
- метрики и уведомления о росте ошибок;
- проверенный fallback на случай исчезновения отзывов из SSR-состояния;
- production-конфигурация с отдельными web- и queue-процессами.
