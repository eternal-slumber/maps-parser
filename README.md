# Review Parser

Тестовое приложение на Laravel 13, Inertia и Vue 3 для импорта организаций и отзывов из публичных страниц Яндекс Карт.

Пользователь может добавить обычную или сокращённую ссылку на организацию, следить за фоновым импортом, переключаться между организациями, фильтровать отзывы по оценке и удалять организации. Отзывы выводятся по 50 записей без перезагрузки страницы.

## Стек

- PHP 8.4, Laravel 13, Sanctum;
- Vue 3, Composition API, Inertia 3, TypeScript;
- MySQL 8.4;
- Redis для очередей и кэша;
- Laravel Sail / Docker Compose;
- Pest и PHPStan.

## Локальный запуск через Docker

Требования: Docker Desktop и Git.

После клонирования проекта установите Composer-зависимости в одноразовом контейнере:

```bash
docker run --rm \
    -u "$(id -u):$(id -g)" \
    -v "$(pwd):/var/www/html" \
    -w /var/www/html \
    laravelsail/php84-composer:latest \
    composer install --ignore-platform-reqs
```

Подготовьте окружение и запустите контейнеры:

```bash
cp .env.example .env
./vendor/bin/sail up -d --build
./vendor/bin/sail artisan key:generate
./vendor/bin/sail artisan migrate --seed
./vendor/bin/sail npm install
./vendor/bin/sail npm run build
```

Приложение будет доступно по адресу <http://localhost:8000>.

Данные сид-пользователя:

```text
Логин:  test@example.com
Пароль: password
```

Для разработки фронтенда вместо production-сборки можно запустить:

```bash
./vendor/bin/sail npm run dev
```

Остановить окружение:

```bash
./vendor/bin/sail down
```

## Как устроен импорт

1. API принимает ссылку и извлекает `businessId`. Сокращённая ссылка раскрывается одним HTTP-запросом без перехода на произвольный внешний домен.
2. Организация сохраняется со статусом `pending`, после чего запускается уникальная queue job.
3. Парсер последовательно загружает SSR-страницы `/maps/org/{businessId}/reviews/?page=N`.
4. Из единственного `script.state-view` декодируется JSON. Организация и массив отзывов выбираются только внутри объекта с нужным `businessId`.
5. Данные проверяются и нормализуются. Обязательные поля отзыва: `reviewId`, `rating`, `updatedTime`; дата допускается только в UTC ISO-формате `YYYY-MM-DDTHH:MM:SS.sssZ`.
6. Собираются все доступные уникальные отзывы, но не более 600 — это наблюдаемый лимит публичной выдачи Яндекса.
7. Только после успешного или ограниченного источником сбора отзывы записываются в БД транзакцией.

Клиент не запускает повторный парсинг при переключении страниц. Импортированные отзывы хранятся в MySQL, а API выполняет серверную пагинацию по 50 записей и фильтрацию по оценке.

## Почему выбран SSR JSON

Рассматривались три варианта.

### SSR embedded JSON — выбранный способ

Плюсы:

- не требует браузера и заметно экономит CPU и память;
- каждая страница сразу содержит структурированные данные;
- `?page=N` позволяет последовательно получить доступную выдачу;
- простой HTTP-клиент удобно запускать в очереди и тестировать через HTTP fake.

Минусы и риски:

- структура `state-view` не является публичным контрактом;
- Яндекс может изменить имена или вложенность полей;
- остаются ограничения источника и CAPTCHA.

### Внутренний `fetchReviews`

Этот путь может отдавать JSON напрямую, но зависит от сессии, CSRF и внутренней подписи запроса. Изменение токенов или механизма подписи сделает интеграцию хрупкой, поэтому он не используется как основной.

### Headless-браузер

Браузер ближе всего повторяет реальное поведение пользователя и может выполнять JavaScript, но работает медленнее, потребляет больше ресурсов и добавляет зависимость от браузера, селекторов и сценария прокрутки. Его имеет смысл рассматривать как отдельный fallback только после появления реальных страниц, которые нельзя получить SSR-запросом.

## Устойчивость к изменению схемы

Парсер не принимает пустой или неоднозначный результат за успешный импорт. Он останавливается с ошибкой, если:

- отсутствует `state-view`, JSON повреждён или имеет неожиданный формат;
- нужная организация не найдена либо объектов с её `businessId` несколько;
- обязательные данные организации отсутствуют или имеют неверный тип;
- массив отзывов внутри нужной организации не найден либо подходящих массивов несколько;
- обязательные поля отзыва отсутствуют, имеют неверный тип или значение;
- `updatedTime` не соответствует ожидаемому ISO-формату;
- до ожидаемого конца получена пустая или полностью повторившаяся страница;
- внутренний лимит страниц достигнут до полного результата.

При таком сбое неполный набор отзывов не записывается, а после исчерпания попыток организация получает статус `failed` и понятный `sync_error`. В журнал Laravel записывается предупреждение с `business_id`, номером страницы и причиной. CAPTCHA и пустой HTTP-ответ также распознаются явно.

Лимит публичного источника в 600 отзывов — ожидаемая ситуация: организация получает статус `limited`, а не `failed`. Равенство количества собранных отзывов общему счётчику Яндекса намеренно не требуется, потому что публичная выдача может содержать только часть всех отзывов.

Посмотреть журнал локально:

```bash
./vendor/bin/sail artisan pail
```

## Очередь, масштаб и прогресс

Парсинг не выполняется внутри HTTP-запроса. `SyncYandexOrganization` отправляется в Redis-очередь, а отдельный контейнер `queue` постоянно запускает worker.

Реализовано:

- уникальная job для организации, чтобы одинаковые импорты не выполнялись параллельно;
- до четырёх попыток с паузами 10, 30 и 60 секунд;
- таймаут job 300 секунд;
- HTTP connect timeout 5 секунд и общий timeout 20 секунд;
- статусы `pending`, `processing`, `completed`, `limited`, `failed`;
- счётчики обработанных страниц и отзывов;
- опрос статуса интерфейсом раз в две секунды.

Для сети из примерно 50 филиалов HTTP-запрос остаётся быстрым: он только создаёт или обновляет организацию и ставит job в очередь. Нагрузку можно масштабировать количеством queue worker, сохраняя общий лимит запросов к Яндексу.

## Антибан на объёме

Сейчас запросы одной организации выполняются последовательно, используются ограниченные таймауты, повторы job с бэкоффом и явное распознавание CAPTCHA. Этого достаточно для прототипа, но не для регулярного массового сбора.

В production нужно добавить:

- общий Redis rate limiter для всех worker, а не независимую задержку в каждой job;
- небольшую случайную паузу между страницами и экспоненциальный бэкофф при `429`, `403`, timeout или CAPTCHA;
- временную остановку импорта по принципу circuit breaker при серии блокировок;
- метрики доли ошибок, CAPTCHA и времени импорта;
- ротацию доверенных прокси и согласованного набора User-Agent только при реальной необходимости.

Прокси нельзя переключать внутри одного импорта без контроля сессии и репутации адресов. CAPTCHA не должна трактоваться как пустая выдача: такой импорт завершается ошибкой и повторяется позднее.

## Идемпотентность и история изменений

Повторное добавление той же организации обновляет существующую запись по `business_id`. Отзывы записываются через upsert, а уникальный индекс `(organization_id, external_id)` защищает от дублей на уровне БД. Изменившиеся автор, текст, оценка и дата обновляются.

Полная история снимков в прототипе не реализована. Для production достаточно добавить:

- `sync_runs`: организация, статус, время начала и окончания, число полученных отзывов, причина ошибки;
- `organization_snapshots`: `sync_run_id`, рейтинг, число оценок и число отзывов;
- `review_snapshots`: `sync_run_id`, `review_id`, текст, оценка и дата публикации.

Тогда текущее состояние останется в `organizations` и `reviews` для быстрого интерфейса, а снимки позволят сравнивать два запуска в формате «было → стало».

## Что было бы доделано при наличии времени

- общий rate limiter, jitter и circuit breaker для массового импорта;
- хранение запусков синхронизации и снимков изменений;
- метрики и оповещения о росте ошибок парсинга;
- проверенный fallback для случаев, когда SSR-состояние перестанет содержать отзывы;
- полноценный production-деплой с отдельными web- и queue-процессами.
