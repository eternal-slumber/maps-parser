# Парсер отзывов Яндекс Карт

## Подтверждённый основной путь

Использовать серверные страницы отзывов:

```text
https://yandex.ru/maps/org/{businessId}/reviews/?page=1
https://yandex.ru/maps/org/{businessId}/reviews/?page=2
https://yandex.ru/maps/org/{businessId}/reviews/?page=3
...
```

Проверено вручную на страницах 1, 2 и 3:

- каждая страница содержала 50 вхождений `reviewId`;
- наборы `reviewId` на разных страницах отличались;
- отзывы находились прямо в embedded JSON внутри HTML.

Это подтверждает, что `?page=N` возвращает самостоятельные SSR-пачки отзывов и подходит для обычного HTTP-парсера без браузера.

## Поток данных

```text
ссылка на карточку
    ↓
businessId
    ↓
GET /maps/org/{businessId}/reviews/?page=N
    ↓
HTML
    ↓
embedded JSON
    ↓
нормализованные данные организации и ReviewDTO[]
    ↓
upsert в БД
```

## Структура embedded JSON

Точное положение объекта внутри HTML — внутренняя деталь Яндекса и может измениться. Не следует считать имя внешнего контейнера стабильным контрактом. Подтверждённая полезная структура каждого отзыва выглядит так:

```json
{
  "reviewId": "hck3KrLN_4qMzqor5LKrwy5tmHSP7VX",
  "author": {
    "name": "Имя автора"
  },
  "text": "Текст отзыва",
  "rating": 5,
  "updatedTime": "дата и время отзыва"
}
```

Минимальное отображение в приложение:

```text
reviewId       → reviews.external_id
author.name    → reviews.author_name
text           → reviews.text
rating         → reviews.rating
updatedTime    → reviews.published_at
```

Дополнительные поля ответа — фотографии, реакции, ответы бизнеса, переводы и уровень автора — для первой версии не нужны.

Из embedded state также нужно получить данные организации, требуемые заданием:

- средний рейтинг;
- количество оценок;
- количество отзывов.

После разбора обязательно проверять наличие ожидаемых узлов и типы значений. Пустой массив нельзя автоматически считать корректным результатом: это может означать изменение разметки.

## Первый spike

Сначала написать отдельный PHP-скрипт без Laravel:

1. Принять ссылку на организацию или `businessId`.
2. Получить HTML одной страницы `reviews/?page=N` обычным HTTP-клиентом с фиксированным `User-Agent`, таймаутами и поддержкой сжатия.
3. Найти JSON-блоки в `<script>` и декодировать их через `json_decode(..., true, flags: JSON_THROW_ON_ERROR)`.
4. Найти коллекцию объектов с `reviewId` и нормализовать только нужные поля.
5. Вывести число отзывов и первые несколько записей.
6. Проверить, что на тестовой карточке получено 50 отзывов и у каждого есть `reviewId`, `author.name`, `rating` и `updatedTime`.

Не извлекать вложенный JSON одной большой регуляркой: регулярное выражение годится для поиска маркера или границ `<script>`, но не для разбора вложенных объектов.

После успешной одной страницы добавить цикл:

```text
page = 1
while страница содержит новые отзывы:
    скачать page
    разобрать отзывы
    отбросить уже встреченные reviewId
    сохранить новые reviewId
    page++
```

Остановка:

- достигнуто известное число страниц, если оно есть в embedded state;
- получена пустая страница;
- страница не дала ни одного нового `reviewId`;
- достигнут защитный лимит страниц, заданный конфигурацией.

Проверка «нет новых `reviewId`» защищает от ситуации, когда Яндекс игнорирует `page=N` и повторяет последнюю или первую страницу.

## Перенос в Laravel

После spike перенести только проверенную логику:

```text
YandexMapsParser
├── извлекает businessId из ссылки
├── загружает SSR-страницу
├── извлекает embedded JSON
├── нормализует организацию и отзывы
└── возвращает обычные массивы или DTO
```

Контроллер должен только валидировать запрос, сохранять ссылку, запускать синхронизацию и возвращать статус. HTTP-запросы к Яндексу и разбор HTML в контроллер не помещать.

Минимальная схема хранения:

- `organizations`: исходная ссылка, `business_id`, рейтинг, число оценок, число отзывов, статус и прогресс синхронизации;
- `reviews`: `organization_id`, `external_id`, автор, текст, оценка, дата публикации;
- уникальный индекс на `(organization_id, external_id)`.

## Queue и прогресс

Полный сбор отзывов запускать через queue/job, а не внутри пользовательского HTTP-запроса.

Минимальный процесс:

1. Сохранить организацию со статусом `pending`.
2. Поставить одну job синхронизации организации в очередь.
3. Job последовательно проходит SSR-страницы, делает upsert и обновляет `processed_pages` и `processed_reviews`.
4. По завершении выставляет `completed`; при окончательной ошибке — `failed` с понятным сообщением.
5. Повторные попытки выполняются с backoff.

Отдельная job на каждую страницу на старте не нужна. Её стоит добавлять только если последовательная обработка одной организации реально не укладывается в лимиты воркера.

## Идемпотентность

`reviewId` использовать как внешний стабильный ключ.

```text
unique: organization_id + reviewId
```

Повторный запуск делает `upsert`:

- новый `reviewId` создаёт запись;
- существующий `reviewId` обновляет автора, текст, рейтинг и дату;
- повтор job после сбоя не создаёт дубли.

Если нужна история изменений, перед обновлением сохранять снимок только когда отслеживаемые поля действительно изменились. Для первой рабочей версии достаточно описать эту модель в README, если история не реализована полностью.

## Ошибки, которые нельзя скрывать

- неверная или неподдерживаемая ссылка;
- организация не найдена;
- сетевой таймаут, DNS/TLS-ошибка или ответ 5xx;
- 403, 429, captcha или страница блокировки;
- пустой HTML;
- JSON не найден или не декодируется;
- исчезли обязательные поля;
- страница повторяет уже полученные `reviewId`;
- счётчики организации противоречат реально полученным данным.

Для временных сетевых ошибок и 429 использовать retry с увеличивающейся паузой. Ошибку структуры не повторять бесконечно: завершить job со статусом `failed`, записать URL, страницу и причину, но не сохранять пустой результат как успешный.

## Что не использовать как основной путь

Не строить первую версию на внутреннем endpoint:

```text
/maps/api/business/fetchReviews
```

Он требует связанного набора динамических параметров и состояния:

```text
csrfToken
sessionId
reqId
s
cookies
```

В экспериментах запрос без корректной web-сессии возвращал только новый `csrfToken`, а подпись `s` менялась вместе с параметрами страницы. Такой путь сильнее зависит от внутренних токенов, cookies и алгоритма подписи.

`fetchReviews` можно оставить как исследованный альтернативный путь или будущий fallback, но не усложнять им основной parser, пока SSR-пагинация работает.

## Критерий готовности

Парсер можно считать готовым к интеграции, когда он:

- принимает ссылку произвольной организации и получает `businessId`;
- проходит все доступные SSR-страницы;
- не сохраняет дубли;
- возвращает нужные поля отзывов и точные счётчики организации;
- отличает корректное отсутствие отзывов от поломки источника;
- безопасно повторяется после частичного сбоя.
